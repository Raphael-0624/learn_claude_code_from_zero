01 · Prompt 的本质：写合同，不是聊天

大多数人用 Claude Code 效果差，根本原因是把它当搜索引擎或聊天机器人用。

💡 正确心智模型
Claude Code 是一个极其聪明但刚入职的工程师。他技术能力极强，但不了解你的项目背景、偏好和禁忌。好的 Prompt = 一份清晰的工作合同。

合同式 Prompt 四要素

要素 1

🎭 角色

他应该扮演什么专家？"你是有 10 年经验的 TypeScript 后端工程师"

要素 2

📦 交付物

具体要什么？"为 UserService 添加邮箱验证功能，包含单元测试"

要素 3

🚫 约束

不能做什么？"不要修改现有 User 实体，不要引入新 npm 包"

要素 4

✅ 验收标准

怎么算完成？"所有测试通过，无 TypeScript 错误，功能本地可运行"

完整合同式 Prompt 示例

角色：你是一个有 10 年经验的 TypeScript 后端工程师，熟悉 NestJS 和 PostgreSQL。

任务：为 UserService 添加邮箱验证功能。

要求：
- 发送验证邮件使用 nodemailer，不要用第三方服务
- 验证 token 存储在 Redis，有效期 24 小时
- 验证成功后更新 user.emailVerified 字段
- 必须包含单元测试，覆盖率 > 90%

约束：
- 不要修改现有的 User 实体结构
- 不要引入新的 npm 包（除非必要）
- 代码风格遵循项目现有规范

验收标准：
- 所有测试通过
- 没有 TypeScript 错误
- 功能在本地可以正常运行

02 · 10种核心 Prompt 模式

模式 1：角色专家模式（Role Expert）

适用场景
需要特定领域专业知识时，给 Claude 一个明确的专家身份 
你是一个专注于 Web 安全的高级工程师，有 OWASP Top 10 的深度经验。
请审查 src/auth/ 目录下的所有代码，找出潜在的安全漏洞。
对每个问题：说明漏洞类型、风险等级（高/中/低）、具体位置、修复方案。

模式 2：分步执行模式（Step-by-Step）

适用场景
复杂任务，防止 Claude 一次性做太多出错，每步确认后再继续 
请按以下步骤完成支付模块重构，每步完成后告诉我，等我确认再继续：

步骤 1：分析现有 payment.service.ts，列出所有需要重构的问题
步骤 2：设计新的接口和类型定义
步骤 3：实现新的 PaymentService
步骤 4：迁移现有测试并补充新测试
步骤 5：更新所有调用方

现在开始步骤 1。

模式 3：约束优先模式（Constraint-First）

适用场景
有明确禁区时，先说不能做什么，Claude 会把约束放在最高优先级 
重要约束（必须遵守）：
- 不要修改 src/legacy/ 目录下的任何文件
- 不要删除任何现有的 API 端点
- 不要升级 package.json 中的依赖版本

在以上约束下，请将 UserController 从 Express 迁移到 NestJS。

模式 4：示例驱动模式（Few-Shot）

适用场景
需要特定格式或风格时，给 2-3 个例子比描述更有效 
请为以下函数写 JSDoc 注释，风格参考这个例子：

【示例】
/**
 * 根据用户 ID 获取用户信息
 * @param {string} userId - 用户唯一标识符
 * @returns {Promise<User | null>} 用户对象，不存在时返回 null
 * @throws {DatabaseError} 数据库连接失败时抛出
 * @example
 * const user = await getUserById('user_123');
 */

现在请用同样的风格为 src/services/ 目录下所有没有注释的函数添加 JSDoc。

模式 5：输出格式控制模式（Output Control）

适用场景
需要结构化输出，用于后续脚本处理 
分析 src/ 目录下所有 TypeScript 文件，找出所有 TODO 注释。

输出格式（严格遵守 JSON）：
{
  "todos": [
    {
      "file": "相对路径",
      "line": 行号,
      "content": "TODO 内容",
      "priority": "high|medium|low",
      "estimated_hours": 预估工时
    }
  ],
  "summary": {
    "total": 总数,
    "by_priority": { "high": 0, "medium": 0, "low": 0 }
  }
}

模式 6：渐进式探索模式（Progressive Exploration）

我刚接手这个项目，请帮我：

第一步：只读取代码，不做任何修改
- 分析项目整体架构
- 找出核心业务逻辑所在的文件
- 识别技术债务和潜在问题

第二步：生成一份架构文档（docs/architecture.md）

第三步：列出你建议优先处理的 5 个问题，按影响程度排序

先做第一步，完成后告诉我。

模式 7：TDD 驱动模式（Test-Driven）

请用 TDD 方式实现购物车模块：

1. 先写测试用例（不要写实现代码）
   - 覆盖所有正常流程
   - 覆盖边界条件（空购物车、超出库存、价格为0等）
   - 覆盖错误场景

2. 给我看测试代码，等我确认

3. 然后写最小实现让测试通过

4. 最后重构优化（保持测试通过）

模式 8：对比分析模式（Compare & Decide）

我需要为项目选择状态管理方案，请对比以下三个选项：
- Zustand / Jotai / Redux Toolkit

对比维度：
1. 学习曲线（1-5分）
2. 与我们项目（React 18 + TypeScript + Next.js 14）的契合度
3. 性能表现
4. 社区活跃度
5. 迁移成本（从现有 Context API 迁移）

最后给出你的推荐和理由。

模式 9：调试侦探模式（Debug Detective）

这个 bug 让我困扰了 2 天，请帮我系统性地排查：

现象：用户登录后，偶发性地（约 10% 概率）出现 401 错误，刷新后恢复正常

已排查：
- JWT token 生成逻辑（看起来正常）
- 前端 token 存储（localStorage，看起来正常）

请：
1. 列出所有可能的原因（不要遗漏）
2. 按可能性排序
3. 为每个原因提供验证方法
4. 从最可能的原因开始，帮我逐一排查

模式 10：文档生成模式（Doc Generator）

请为这个项目生成完整的 API 文档：

要求：
- 格式：OpenAPI 3.0 YAML
- 扫描 src/controllers/ 下所有控制器
- 从代码和注释中提取接口信息
- 为每个接口生成：描述、参数、请求体、响应示例、错误码
- 保存到 docs/api.yaml

同时生成一份 Markdown 版本（docs/api.md），面向前端开发者，语言友好。

03 · CLAUDE.md 写法完全指南

六种 CLAUDE.md 类型

类型 A

🚫 约束型

专注于告诉 Claude 不能做什么，适合有历史包袱的项目

类型 B

🎭 角色型

给 Claude 一个明确的专家身份，适合专业领域项目

类型 C

📋 流程型

定义工作流程，适合有严格开发规范的团队

类型 D

📖 上下文型

提供项目背景，适合复杂业务系统

类型 E

🔧 工具型

告诉 Claude 项目的工具链，减少猜测

类型 F ⭐

🔀 混合型（推荐）

综合以上类型，200 行以内的完整配置

混合型 CLAUDE.md 模板（推荐）

# [项目名] Claude Code 配置

## 项目概述
[一句话描述项目]

## 技术栈
- 运行时：Node.js 20 LTS
- 框架：NestJS 10
- 数据库：PostgreSQL 15 + TypeORM

## 常用命令
- 启动：`npm run start:dev`
- 测试：`npm test`
- 构建：`npm run build`

## 代码规范
- 使用 TypeScript 严格模式
- 所有新函数必须有单元测试
- 禁止使用 any 类型

## 重要约束
- 不要修改 src/legacy/ 目录
- 不要直接操作数据库（必须通过 Repository 层）
- 不要硬编码任何配置值

## 已知问题（暂时不要修改）
- auth.service.ts 第 142 行：已知 JWT 刷新 bug，正在修复

5 个反模式

反模式问题修复方法
超过 200 行Claude 遵循质量下降精简到核心约束，细节放子目录 CLAUDE.md
写"尽量"、"最好"模糊指令，Claude 会忽略改为"必须"、"禁止"等明确词
只写技术栈，不写约束Claude 不知道边界在哪加入禁止操作和已知问题
复制粘贴 README信息冗余，稀释重要内容只写 Claude 需要知道的
从不更新项目演进后 CLAUDE.md 过时每次重大重构后更新

04 · 任务类型 Prompt 模板库

代码重构

请重构 [文件/模块]，目标：[重构目标]

当前问题：
- [问题1]
- [问题2]

重构要求：
- 保持所有现有测试通过
- 保持对外接口不变（[列出接口]）
- 遵循 [设计模式/原则]

请先分析现有代码，给我重构方案，等我确认后再执行。

单元测试

请为 [文件] 编写完整的单元测试。

测试框架：[Jest/Vitest/Mocha]
覆盖要求：
- 所有 public 方法
- 正常流程 + 边界条件 + 错误场景
- 覆盖率目标：> 90%

注意：[项目特殊约定，如数据库 mock 方式]

Bug 修复

Bug 描述：[现象]

复现步骤：
1. [步骤1]
2. [步骤2]

期望行为：[应该发生什么]
实际行为：[实际发生什么]
错误日志：[粘贴错误日志]

请：
1. 定位根本原因
2. 提出修复方案（如有多个方案，说明优劣）
3. 实现修复
4. 添加防止回归的测试

代码审查

请对以下代码进行严格的代码审查：
[粘贴代码 或 指定文件路径]

审查维度：
1. 正确性：逻辑是否正确，有无 bug
2. 安全性：有无安全漏洞（SQL 注入、XSS、权限绕过等）
3. 性能：有无明显性能问题
4. 可维护性：代码是否清晰，命名是否合理

输出格式：
- 每个问题：[严重程度] 文件:行号 - 问题描述 - 修复建议
- 最后给出总体评分（1-10）和主要改进建议

性能优化

这个接口响应时间过长（平均 [X]ms，目标 [Y]ms）：
[接口路径或代码]

请：
1. 分析可能的性能瓶颈（基于代码分析，不要猜）
2. 按影响程度排序
3. 对每个瓶颈提供优化方案和预期收益
4. 从收益最大的开始实施

约束：
- 不能改变接口的输入输出格式
- 不能引入新的基础设施

05 · 常见失败 Prompt 修复手册

失败案例 1：太模糊

❌ 失败 Prompt
帮我优化一下这个项目的代码
✅ 修复后
请对 src/services/user.service.ts 进行代码质量优化：
- 目标：提高可读性和可维护性
- 不要改变任何公共方法的签名
- 不要改变业务逻辑
- 优化后运行 npm test 确保测试通过
- 列出每处修改和修改原因

失败案例 2：任务太大

❌ 失败 Prompt
帮我把整个项目从 JavaScript 迁移到 TypeScript
✅ 修复后
我需要将项目从 JS 迁移到 TS，请先帮我制定迁移计划：

1. 分析项目规模（文件数量、复杂度）
2. 识别迁移风险点
3. 制定分阶段方案（每阶段不超过 20 个文件）
4. 估算每阶段工时

先只做计划，不要修改任何代码。

失败案例 3：用了攻击性语言

❌ 失败 Prompt（新版 Claude 会表现更差）
你必须！！！绝对不能！！！修改 legacy 目录！！！
这非常非常重要！！！
✅ 修复后
重要约束：请不要修改 src/legacy/ 目录下的任何文件。
原因：这些文件有外部系统依赖，修改会导致生产事故。

失败案例 4：没有验收标准

❌ 失败 Prompt
帮我写一个用户认证系统
✅ 修复后
请实现用户认证系统，完成标准：

功能：注册、登录、刷新Token、登出、忘记密码
质量：测试覆盖率 > 85%，有 Swagger 文档
安全：bcrypt 加密，登录失败5次锁定30分钟

06 · 上下文管理策略

上下文的黄金法则

⚠️ 重要
重要信息放在 Prompt 开头，Claude 对开头和结尾的注意力最强，中间容易"遗忘"。

长会话管理

会话长度建议操作
< 30 轮正常使用
30-60 轮使用 /compact 保留[关键信息]
> 60 轮开新会话，用 CLAUDE.md 传递上下文
跨天任务用 claude --continue 恢复，先让 Claude 总结进度

跨会话上下文传递

# 结束会话前，让 Claude 生成上下文摘要
> 请生成一份工作摘要，包含：
  1. 已完成的工作
  2. 当前状态
  3. 下一步计划
  4. 需要注意的问题
  保存到 .claude/session-notes.md

# 下次开始时
> 请先阅读 .claude/session-notes.md，了解上次的工作进度，然后继续。

08 · 高级技巧：XML 结构化 Prompt

对于复杂任务，使用 XML 标签可以显著提高 Claude 的理解准确度：

<task>
  <role>高级 TypeScript 工程师，专注于性能优化</role>
  
  <context>
    这是一个电商平台的订单服务，日均处理 10 万笔订单。
    当前 getOrderList 接口平均响应时间 800ms，目标 200ms。
  </context>
  
  <constraints>
    <must_not>修改数据库 schema</must_not>
    <must_not>改变接口的输入输出格式</must_not>
    <must>保持所有现有测试通过</must>
    <must>添加性能测试</must>
  </constraints>
  
  <deliverables>
    <item>优化后的代码</item>
    <item>性能对比报告（优化前后）</item>
  </deliverables>
  
  <input>
    请分析 src/order/order.service.ts 中的 getOrderList 方法
  </input>
</task>
场景推荐方式
简单任务（< 3 个要求）普通文本
中等复杂度Markdown 列表
高度复杂（多约束、多交付物）XML 结构
需要精确解析的输出XML + JSON 输出格式

Prompt 质量自检清单

在发送 Prompt 前，检查以下项目：

角色：是否指定了 Claude 应该扮演的专家角色？
任务：任务描述是否具体，没有歧义？
约束：是否列出了所有禁止操作？
验收：是否定义了完成标准？
格式：是否指定了输出格式？
规模：任务是否太大？是否需要拆分？
上下文：是否提供了必要的背景信息？
不确定性：是否告诉 Claude 遇到不确定时怎么处理？
