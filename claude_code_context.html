Context 上下文系统

Token 窗口是 Claude 的工作记忆。理解它如何工作、如何压缩、如何腐烂，是高效使用 Claude Code 的关键所在。

1

上下文窗口的组成

上下文窗口是 Claude 在单次会话中能够"看到"的全部信息，是一个有限的 token 空间。

典型项目会话的 Token 分布（200K 窗口）
💬

系统提示 + CLAUDE.md

约 10% (~20K tokens)。项目指令和 Claude 的行为规范，每次会话自动加载。

🗣️

对话历史

约 20% (~40K tokens)。用户消息和 Claude 回复的完整记录。

📄

文件内容

约 30% (~60K tokens)。通过 read 工具读取的代码文件内容。

🔧

工具输出

约 40% (~80K tokens)。bash/grep/read 等工具的执行结果，最大消耗者。

3

三级压缩机制

Level 1: MicroCompact（微压缩）

裁剪冗余工具输出、截断过长响应，信息损失极低

触发：使用率 > 50% 节省：10-20% 损失：极低

Level 2: AutoCompact（自动压缩）

生成对话摘要，替换原始历史，保留关键决策和错误信息

触发：使用率 > 64-75% 节省：40-60% 损失：低

Level 3: Full Compact（完全压缩）

激进压缩，只保留最关键信息，紧急情况下触发

触发：使用率 > 90% 节省：70-80% 损失：中
三级压缩效果对比（Token 节省量）
# 压缩管理命令
claude /status          # 查看当前上下文使用情况
claude /compact         # 手动触发 AutoCompact
claude /compact --full  # 强制完整压缩
4

"中间遗失"问题

研究表明，Claude 对上下文的注意力分布呈 U 形曲线——开头和结尾注意力强，中间内容容易被遗忘。

注意力分布曲线（U 形效应）

实际影响与解决方案

📌

关键信息置顶

将最重要的约束和规范放在 CLAUDE.md 的最前面，确保始终被注意到

🔄

定期重申约束

在长会话中，定期重申关键约束："记住我们使用 PostgreSQL..."

🗜️

主动压缩

使用 /compact 重置上下文，保留关键信息，清除噪音

5

上下文腐烂（Context Rot）

随着会话进行，上下文中积累大量历史信息，导致信噪比下降、注意力分散、性能下降。

腐烂症状识别

🔁
Claude 开始重复之前已经讨论过的内容
🧠
Claude 忘记了之前确认的技术决策
😰
响应变得更加保守和不确定
❓
Claude 开始询问已经提供过的信息
🐛
代码质量下降，出现之前已修复的错误
⏱️
响应速度变慢，思考时间增加
⚠️ 对抗腐烂：建议每 30-50 轮对话执行一次 /compact，或者为独立任务开启新会话。将重要决策写入 CLAUDE.md 是最可靠的防腐烂方案。
6

子 Agent 的上下文隔离

😰

主 Agent 上下文（已满 80%）

大量对话历史 + 多个文件内容 + 工具调用历史，快要撑不住了

✨

子 Agent 上下文（全新 0%）

独立的 200K token 窗口，只接收精简的任务描述和关键约束

💡 最佳实践：向子 Agent 传递精简的上下文，只包含完成任务所需的最少信息。子 Agent 完成后只返回结果摘要，不返回完整的执行历史。
7

上下文优化技巧

文件读取优化

# ❌ 不好：读取整个大目录
claude "读取 src/ 目录下所有文件"

# ✅ 好：只读取需要的部分
claude "只读取 src/auth/ 目录下的认证相关文件"

# ✅ 更好：先搜索，再精确读取
claude "先用 grep 找到处理登录的函数，然后只读取那个函数"

会话分割策略

🔙

会话 1：后端 API

专注于 API 设计和实现，保持上下文干净

🖥️

会话 2：前端组件

专注于 UI 开发，不混入后端细节

🧪

会话 3：测试

专注于测试编写，引用 API 文档而非实现细节
